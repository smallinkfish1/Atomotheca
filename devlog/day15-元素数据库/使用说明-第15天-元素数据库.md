# 使用说明 · 第 15 天 · 元素数据库（Atomotheca 模块第 1 天）

> 本文是第 15 天的**完整交付说明**，包含 Prompt 要求的六段式内容。
> 原理推导另见 `docs/第15天实现功能原理.md`。

---

## 一、今日目标

把元素的基础数据从 C++ 代码里搬进 JSON 文件，写一个能读它、能校验它、能算电子排布和离子的数据层。

一句话验收：`./build/molecule_viewer --dump Fe` 能打印出 `1s2 2s2 2p6 3s2 3p6 3d6 4s2`，以及 `Fe2+ → 3d6`、`Fe3+ → 3d5`。

---

## 二、核心概念（简述版）

完整推导见原理文档，这里只列结论，方便你对照代码读。

1. **一个亚层 = 三个数**：`n`（第几层）、`l`（s/p/d/f）、电子数。
   容量公式 `2×(2l+1)`：s 装 2、p 装 6、d 装 10、f 装 14。代码里是 `subshellCapacity()`。

2. **书写顺序 ≠ 填充顺序**。这是最容易写错的地方：
   - 书写顺序（教科书怎么写）：先按 `n`，再按 `l` → `... 3d 4s`
   - 填充顺序（电子实际先占哪）：Madelung 规则，`n+l` 小的先 → `... 4s 3d`
   - 代码里两个函数：`sortByShell()` 和 `sortByEnergy()`，别用混。

3. **电离顺序不能从填充顺序反推**。电子被拿走时，**最外层（n 最大）先走**，
   `n` 相同则 `l` 大的先走。所以 Fe 失去 2 个电子后是 `3d6`（4s² 先没了），
   不是 `3d4 4s2`。这条在 Prompt 第 9 节的踩坑表里已经记过一次，代码里 `makeIon()` 是照着它写的。

4. **数据驱动**：`elements.json` 是唯一数据源。以后加元素、改离子，只改 JSON，不重编译。

## 三、架构建议

### 新增

```
src/orbital/element.h      声明：Subshell / Ion / Element / ElementDatabase + 排序格式化自由函数
src/orbital/element.cpp    实现：JSON 解析、校验、排布格式化、离子推算、控制台报告
assets/data/elements.json  21 个元素（H–Ca + Fe）的全部化学数据
external/json/nlohmann/json.hpp   nlohmann/json v3.11.3 单头文件（919,975 字节）
```

### 修改

```
CMakeLists.txt   源码列表加 src/orbital/element.cpp；include 路径加 external/json
src/main.cpp     启动时加载数据库；新增 --dump <符号>；--help 补说明
```

### 为什么这样分

- `element.h` 里**只有声明**，一个 `#include <nlohmann/json.hpp>` 都没有。
  JSON 类型只出现在 `element.cpp` 内部 —— 否则每个 include 这个头文件的 .cpp
  都要花 2~3 秒编译那 900 KB 的头文件。这是头文件卫生，不是洁癖。
- `element.*` 不 include 任何图形库（铁律 2）。`--dump` 可以在没有显卡的 CI 上跑，
  这就是解耦的直接收益。
- 数据进 `assets/data/` 而不是 `src/`，因为它是**资源**不是代码：
  `assets/` 已经会被 POST_BUILD 拷到 exe 旁边、被 Emscripten `--preload-file` 打包，
  放这儿零成本获得跨平台分发能力。

## 四、改动内容（逐文件）

### 4.1 新增 `external/json/nlohmann/json.hpp`

从官方 release 拉的 v3.11.3 **单头文件**（不是拆分的 `detail/` 版本）：

```
https://github.com/nlohmann/json/releases/download/v3.11.3/json.hpp
```

- 大小 919,975 字节，纯头文件，无编译依赖，无包管理器。
- 在 Prompt 的 5 MB 上限内。
- 系统里 `/usr/include/nlohmann/` 其实已经有一份同版本，但那是**拆分版**
  （`json.hpp` + `detail/*.hpp` 一堆文件），单独拷一个 `json.hpp` 编不过。
  为了"clone 下来就能编、CI 不用装包、版本锁死"，选择 vendor 单头文件进仓库。

### 4.2 新增 `assets/data/elements.json`

结构如下（不是随手拍的，字段和 `Element` 结构体一一对应）：

```json
{
  "version": "1.0",
  "source": "...",
  "elements": [
    {
      "symbol": "O",
      "name": "Oxygen",
      "nameZh": "氧",
      "atomicNumber": 8,
      "atomicMass": 15.999,
      "period": 2,
      "group": 16,
      "category": "nonmetal",
      "cpkColor": [1.00, 0.05, 0.05],
      "subshells": [ { "n": 1, "l": 0, "e": 2 },
                     { "n": 2, "l": 0, "e": 2 },
                     { "n": 2, "l": 1, "e": 4 } ],
      "commonIons": [-2]
    }
  ]
}
```

几个刻意的设计决定：

| 决定 | 原因 |
|---|---|
| 亚层写成 `{"n":2,"l":1,"e":4}` 而不是字符串 `"2p4"` | 字符串要写解析器，容易出错；三个整数直接可用，Day 17 画能级图也直接吃这个结构 |
| `commonIons` 只存**电荷**，不存排布 | 排布由 `makeIon()` 推算。数据少一半，且不会出现"JSON 里写的和推算的对不上"——加载时还会校验两者一致 |
| 存了 `nameZh` 但 UI 不显示 | 数据层先备好，等哪天加载了中文字体直接用，不用改数据文件 |
| `cpkColor` 用 0~1 浮点 | 已经是 OpenGL 的色域，省一次 `/255` |
| 顶层是对象不是裸数组 | 将来要加 `"version"`、`"source"`、甚至 `"orbitals"` 数据时不用改结构 |

覆盖范围：H、He、Li、Be、B、C、N、O、F、Ne、Na、Mg、Al、Si、P、S、Cl、Ar、K、Ca、Fe，共 **21 个**。
（按 Prompt 的描述补到 H–Ca + Fe。21–25 号元素缺失，Day 16 画周期表时这几格会是空的，届时再按你的决定补。）

### 4.3 新增 `src/orbital/element.h`

公开 API 一览：

| 名字 | 作用 |
|---|---|
| `Subshell{n,l,electrons}` | 一个亚层 |
| `subshellCapacity(l)` | 容量 `2(2l+1)` |
| `sortByShell()` / `sortByEnergy()` | 书写顺序 / 填充顺序，**两个别用混** |
| `formatConfig()` / `formatConfigOrdered()` | 前者会先排序，后者保持传入顺序 |
| `countElectrons()` | 电子总数 |
| `Ion{charge,subshells}` + `label()` | 离子，`label("Fe")` → `"Fe2+"`；±1 时省略数字（`H+`） |
| `Element` | 元素，含 `configString()`、`energyOrderedSubshells()`、`makeIon()` |
| `ElementDatabase` | `loadFromFile()` / `find()` / `findByZ()` / `elements()` |
| `describe(e)` | 生成控制台报告文本，`--dump` 用的就是它 |

### 4.4 新增 `src/orbital/element.cpp`

关键实现点（完整代码见文件）：

**① Madelung 序列是算出来的，不是打表**

```cpp
// n+l 从小到大；同和值 n 小的先
for (int sum = 1; sum <= 10; ++sum)
    for (int n = 1; n <= sum; ++n) {
        const int l = sum - n;
        if (l < 0 || l > 3) continue;
        if (l >= n) continue;        // 排除 1p、2d 这类不存在的组合
        seq.emplace_back(n, l);
    }
```

产出 `1s 2s 2p 3s 3p 4s 3d 4p 5s 4d ...`，和课本上那张图完全一致。
写死表格也能用，但规则只要三行代码，写死 20 行数据反而更容易错。

**② 阳离子：先失最外层**

```cpp
// 每一轮扫一遍所有亚层，挑 n 最大的；n 相同挑 l 最大的
if (cur.n > keep.n || (cur.n == keep.n && cur.l > keep.l))
    best = i;
ion.subshells[best].electrons -= 1;
```

逐个剥而不是一次性算，是为了 `Fe3+` 这种要跨亚层剥的情况能正确处理。

**③ 阴离子：按能级顺序找第一个没住满的**

对 `O2-`：`1s`(满) → `2s`(满) → `2p`(4/6) → 塞两个 → `2p6`。
如果全都满了会新建下一个亚层，虽然当前数据用不到。

**④ 加载时做三道校验，错一个字都编不过**

1. 字段级：`n` 在 1..7、`l` 在 0..3、`l < n`、`0 ≤ e ≤ 容量`。
2. 元素级：亚层不重复；**电子总数必须等于原子序数**（这条能抓出 90% 的手写错误）。
3. 推算自检：对每个 `commonIons` 真的调一次 `makeIon()`，检查电子数是否等于 `Z - q`。

第 3 条看着多余（`makeIon` 是自己写的），但它是唯一能保证"数据和算法不脱节"的手段。
哪天有人改了 `makeIon` 的顺序逻辑，加载时立刻会炸，而不是等到 Day 16 界面显示怪东西才发现。

**⑤ 异常安全**

解析先进临时的 `parsed` 数组，全部成功才 `elements_.swap(parsed)`。
失败时数据库保持为空，不会留下"前 5 个元素能用、第 6 个崩了"的半残状态。

### 4.6 修改 `src/main.cpp`

**改动 1：include 数据层头文件**

```diff

```

**改动 2：全局数据库 + 加载函数**（放在 `AppState g_app;` 之后）

```diff
 AppState g_app;
+
+// ==================== Atomotheca 元素数据库 ====================
+// 第 15 天：化学数据全部来自 assets/data/elements.json，C++ 里不硬编码。
+// 数据层加载失败不影响分子查看器的正常使用，只是周期表面板暂时不可用。
+orbital::ElementDatabase g_elements;
+
+static bool loadElementDatabase(std::string* error)
+{
+    const std::string path = pathutil::resolveResource("assets/data/elements.json");
```

## 六、排错清单

| 现象 | 根因 | 处理 |
|---|---|---|
| `fatal error: nlohmann/json.hpp: No such file` | `external/json` 没进 include 路径，或单头文件放错层级 | 正确路径是 `external/json/nlohmann/json.hpp`，include 写 `#include <nlohmann/json.hpp>` |
| 用了系统里的 `/usr/include/nlohmann/json.hpp`，拷到别的机器编不过 | 系统版是**拆分版**，依赖 `detail/` 一堆文件 | 别拷那一个文件，用 release 里的单头文件 |
| `undefined reference to orbital::ElementDatabase::loadFromFile` | `element.cpp` 没加进 `add_executable` | 见 4.5 的 diff |
| 打不开 `assets/data/elements.json` | POST_BUILD 只在**链接过**时才拷贝；只改 JSON 不重编，`build/assets/` 里还是旧的 | 改完 JSON 手动 `cp -r assets build/`，或碰一下任意源文件再编一次 |
| `--dump` 输出"元素数据库加载失败"但文件明明在 | 从别的目录运行，且 exe 附近没有 assets | 在项目根目录跑，或 `cd build && ./molecule_viewer --dump O` |
| JSON 报错 `字节偏移 1234` | 数错花括号/逗号 | `python3 -m json.tool assets/data/elements.json` 快速定位 |
| 校验报"电子总数与原子序数不符" | 手写 subshells 时漏写/多写亚层 | 对照 `n+l` 顺序重算一遍；不要凭记忆 |
| 校验报"离子 X 推算得 N 个电子，应为 M" | `makeIon()` 逻辑被改坏 | 这是自检机制在工作，别绕过它，去查 `makeIon()` |
| `H1+` 这种显示 | 没做 ±1 省略 | `Ion::label()` 里判断 `abs(charge) > 1` 才拼数字 |
| Windows 上中文乱码 | MSVC 需要 `/utf-8` | CMakeLists 里已有 `/utf-8`，MinGW 默认 UTF-8 |
| 编译变慢 2~3 秒 | 900 KB 的 JSON 头文件被多个 .cpp include | 只在 `element.cpp` 里 include，头文件绝不 include 它 |
| **启动报「GLFW 初始化失败」，无其它信息** | GLFW 编译时没编进 X11/Wayland 后端，只剩 null 后端 | 见下方「补丁记录」 |
| **配置阶段报 `Xinerama headers not found`** | 用 external/glfw 源码在 Linux 上编，缺 4 个 X 开发包 | `sudo apt install libxinerama-dev libxcursor-dev libxi-dev libxrandr-dev`，或直接用系统 `libglfw3-dev` |

## 八·五、补丁记录

### 补丁 1（2026-11-14）：启动时「GLFW 初始化失败」

**现象**

```
$ ./molecule_viewer
元素数据库: 21 个元素  |  示例 O: 1s2 2s2 2p4
[错误] GLFW 初始化失败！
```

**排查过程**

1. `grep GLFW_BUILD build/CMakeCache.txt` →
   ```
   GLFW_BUILD_WAYLAND:BOOL=OFF
   GLFW_BUILD_X11:BOOL=OFF
   ```
2. `ldd build/molecule_viewer | grep -i x11` → 什么都没有，一个 X 库都没链接。
3. `ls build/external/glfw/src/CMakeFiles/glfw.dir/` → 只有 `null_init.c.o`、
   `null_window.c.o`、`null_monitor.c.o`，没有 `x11_*.o`。

结论：GLFW 被编成了一个**没有任何窗口后端**的库。它能编译、能链接、能跑，
但 `glfwInit()` 唯一能返回的结果就是失败。

**根因**

`CMakeLists.txt` 里这几行：

```cmake
set(GLFW_BUILD_WAYLAND  OFF CACHE BOOL "" FORCE)
set(GLFW_BUILD_X11      OFF CACHE BOOL "" FORCE)
```

本来是为了让 MinGW 交叉编译 Windows 时少找依赖，但它们**没有加条件**，
所以 Linux 原生构建也生效了。GLFW 的 CMake 逻辑是：X11 和 Wayland 都关掉 →
退化成 null 后端 → 编译通过、运行必挂。

而且这是个「沉默的坑」：以前 `external/glfw` 是个空的 gitlink，
CMake 走 `find_package(glfw3)` 用系统库，一切正常。
等哪天为了 MinGW 把 `external/glfw` clone 下来，原生构建就悄悄坏掉了，
坏的时候一句原因都不给。

**修复**

1. `CMakeLists.txt`：改成**原生构建优先用系统 GLFW**，交叉编译才用源码；
   X11/Wayland 的开关只在目标为 Windows 时才强制 OFF，其余情况 `unset` 掉缓存
   （`FORCE` 写进 `CMakeCache.txt` 的值，不显式清除是不会失效的）。
2. `main.cpp`：加 `glfwSetErrorCallback`，让 GLFW 把真实原因打到 stderr；
   窗口创建失败时补一段排查提示。

**修复后的对照**

| | 修复前 | 修复后 |
|---|---|---|
| CMake 选的 GLFW | 源码编译（null 后端） | 系统库 3.4.0 |
| `ldd` 里的依赖 | 无 X11、无 libglfw | `libglfw.so.3` |
| `glfwInit()` | 失败 | 成功 |

**复查方式**

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release | grep GLFW
# 应该看到: --   GLFW       : 系统库 3.4.0
ldd build/molecule_viewer | grep glfw        # 应有 libglfw.so.3
```

MinGW 交叉编译路径已回归验证：`cmake ... -DCMAKE_TOOLCHAIN_FILE=cmake/toolchain-mingw64.cmake`
仍然输出 `--   GLFW       : 源码编译 (external/glfw)`、`System : Windows`，未受影响。

## 七、Git commit 建议

拆成三个提交，每个都能单独编译通过：

```bash
# 1. 第三方依赖：单头文件 JSON
git add external/json/nlohmann/json.hpp
git commit -m "build: 引入 nlohmann/json 3.11.3 单头文件（external/json）"

# 2. 数据文件
git add assets/data/elements.json
git commit -m "feat(data): 新增 elements.json，21 个元素的排布与常见离子

覆盖 H–Ca + Fe。亚层用 {n,l,e} 三个整数表示，离子只存电荷、排布由代码推算。
cpkColor 用 0~1 浮点，直接对接 OpenGL 色域。"

# 3. 代码接入
git add src/orbital/element.h src/orbital/element.cpp src/main.cpp CMakeLists.txt
git commit -m "Day 15: 元素数据库与电子排布（Atomotheca 模块第 1 天）

- 新增 orbital/element.{h,cpp}：JSON 解析、三道校验、书写/填充双排序、离子推算
- 阳离子按「先失最外层」剥电子，Fe2+ 得 3d6（不是 3d4 4s2）
- main.cpp 启动时加载数据库；新增 --dump <符号> 做数据层验证
- CMakeLists 加 element.cpp 与 external/json include 路径

数据层不依赖 OpenGL，--dump 可在无显卡环境（CI）运行。"
```
