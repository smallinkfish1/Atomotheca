## 1. 为什么要把数据搬出代码

第 1 天到第 14 天，元素颜色写在 `molecule.h` 的 `if (element == "C")` 里。
到第 15 天不行了：每个元素要存原子序数、原子量、周期、族、类别、CPK 颜色、
若干个亚层、若干个常见离子……21 个元素就是几百个字段。

如果继续硬编码，会变成这样：

```cpp
// 千万别这么写
elements.push_back({ "Fe", 26, 55.845, 4, 8, "transition-metal",
                     {0.88f, 0.40f, 0.20f},
                     { {1,0,2}, {2,0,2}, {2,1,6}, {3,0,2}, {3,1,6}, {3,2,6}, {4,0,2} },
                     {2, 3} });
```

问题不在"长"，在于：

1. **改数据要重编译**。加一个元素 → 改 .cpp → 重新编译 → 重新链接。几十秒没了。
2. **数据错误编译器查不出来**。`{3,2,6}` 和 `{3,2,7}` 在编译器眼里都是合法整数。
3. **改错一个数没有报错**，只会在界面上一脸懵。

放进 JSON 之后，这三条全部反转：改文件立即生效（甚至不用重启程序），
写错能在加载时被校验器拦下来，报错精确到"第 8 个元素（O）的 2p 亚层电子数超容量"。

**代价**：启动时要读文件、要解析。这个代价是毫秒级，值得。

## 2. 一个亚层需要几个数（容量公式的来历）

电子在原子里的状态由一组量子数描述。和"能装几个"直接相关的有两个：

- **n（主量子数）**：第几层电子层，1、2、3…。n 越大，离核越远，能量越高。
- **l（角量子数）**：这一层里的"形状"，0=s、1=p、2=d、3=f。l 越大，能量略高。

然后是 **m（磁量子数）**：给定 n 和 l，m 可取 `-l, -l+1, …, 0, …, l-1, l`，
一共 **2l+1** 个取值。每一个取值对应**一个轨道**。

再加 **自旋**：每个轨道最多容纳 2 个电子（自旋相反，一上一下）。这是泡利不相容原理。

于是：

```
一个亚层的最多电子数 = 2 × (2l + 1)
```

| l | 名字 | 轨道数 2l+1 | 最多电子数 |
|---|---|---|---|
| 0 | s | 1 | 2 |
| 1 | p | 3 | 6 |
| 2 | d | 5 | 10 |
| 3 | f | 7 | 14 |

代码里就是一行：

```cpp
int subshellCapacity(int l) { return 2 * (2 * l + 1); }
```

**记住 2 / 6 / 10 / 14 这四个数**，后面全靠它。

还有一条容易忽略的约束：**l 必须小于 n**。所以 `1p`、`2d`、`3f` 这些亚层不存在。
代码里的 `if (l >= n) continue;` 就是在挡这个 —— 这不是防御性编程，是物理事实。

## 3. 电子怎么排：三条规则

### 规则一：能量最低原理（Aufbau）

电子总是先填能量低的亚层。问题是"哪个更低"。

答案不是简单地"n 小的更低"。真实规律由 **Madelung 规则** 给出：

> 按 **(n + l) 从小到大** 填；`n+l` 相同时，**n 小的先填**。

我们算一遍：

| 亚层 | n | l | n+l | 填充次序 |
|---|---|---|---|---|
| 1s | 1 | 0 | 1 | 1 |
| 2s | 2 | 0 | 2 | 2 |
| 2p | 2 | 1 | 3 | 3 |
| 3s | 3 | 0 | 3 | 4 |
| 3p | 3 | 1 | 4 | 5 |
| **4s** | 4 | 0 | **4** | **6** |
| **3d** | 3 | 2 | **5** | **7** |
| 4p | 4 | 1 | 5 | 8 |

看到关键点了吗：`4s` 的 `n+l = 4`，`3d` 的 `n+l = 5`，
所以 **4s 比 3d 先填**，尽管 4s 的 n 更大。这就是课本上那个著名的"能级交错"。

### 但为什么会有交错？（不只是数学巧合）

`n+l` 规则不是凭空来的，它背后是**屏蔽效应**和**穿透效应**：

- 内层电子会"挡住"原子核的正电荷，让外层电子实际感受到的吸引减弱（屏蔽）。
- 但 s 轨道的电子云在核附近有分布（穿透能力强），能"钻"进内层，受屏蔽少，
  所以同一层的 s 比 p 能量低，p 比 d 低。
- 4s 虽然 n=4，但它的穿透能力强到足以让能量低于 3d。

一个常用的物理图像：3d 电子云形状复杂、大部分时间离核远，且被 3s3p 屏蔽得厉害；
4s 虽然主壳层更外，但能钻进内层"贴脸"感受核电荷，所以反而更稳定。

> 这个解释是定性的。严格的定量要靠自洽场计算，超出本项目范围。
> 你只需要知道：`n+l` 规则是这套物理的图像化总结，不是人为规定。

### 规则二：泡利不相容

一个轨道最多两个电子，且自旋必须相反（↑↓）。

表现为：填到一个亚层时，必须先把它的容量填满，才能进下一个亚层。

### 规则三：洪特规则

同一个亚层的多个轨道能量相同（简并）。电子会**先单独占据不同的轨道，且自旋平行**，
等每个轨道都有一个电子了，才开始配对。

例子：氮 `2p³`，不是"一个轨道塞 2 个 + 另一个塞 1 个"，而是三个轨道各一个：

```
2p:  ↑   ↑   ↑     ← 正确（洪特）
2p:  ↑↓  ↑   ·     ← 错误
```

**注意**：Day 15 的数据层只存"某个亚层有几个电子"，不存"怎么分布在轨道上"。
洪特规则要到 **Day 17 画能级图** 才真正用上 —— 那时候才需要知道
`2p³` 该画成 `↑ ↑ ↑` 还是 `↑↓ ↑`。数据层给的是 3 这个数字，画图时再按洪特规则展开。

## 4. 两种顺序，必须分清

这是第 15 天最容易写错、且错了最难发现的地方。

**书写顺序**（教科书上印出来的样子）：先按 `n`，再按 `l`。

```
Fe: 1s² 2s² 2p⁶ 3s² 3p⁶ 3d⁶ 4s²
                                  ↑ 注意 3d 写在 4s 前面
```

**填充顺序**（电子实际先占哪个）：按 `n+l`。

```
Fe 实际填充过程: 1s² 2s² 2p⁶ 3s² 3p⁶ 4s² 3d⁶
                                            ↑ 4s 先填满，最后 6 个电子进 3d
```

两个字符串的字符组成完全一样，顺序不同。

**为什么教科书要按 n 排？** 因为按电子层/周期分组看更方便：读者想看"第 3 层有几个电子"，
按 n 排一眼就能数。教学便利，不是物理事实。

**为什么代码里两个都要有？**

| 用途 | 用哪个 | 原因 |
|---|---|---|
| 显示排布式（Day 16 面板） | 书写顺序 | 和课本对得上，用户不会觉得写错了 |
| 画能级图（Day 17） | 填充顺序 | 图要体现"4s 在 3d 下面"，必须按能量排 |

所以 `element.h` 有两个函数：

```cpp
std::vector<Subshell> sortByShell(std::vector<Subshell>);   // n → l
std::vector<Subshell> sortByEnergy(std::vector<Subshell>);  // n+l → n
```

**踩过的坑**：我第一版 `formatConfig()` 内部无条件先 `sortByShell` 一遍，
结果拿 `sortByEnergy` 的结果去格式化，又被排回书写顺序了 —— 于是 Fe 的
"填充次序"那一行永远显示成和"排布式"一模一样，肉眼看不出错，只是信息丢了。
修法是拆出 `formatConfigOrdered()`（保持传入顺序），`formatConfig()` 继续无脑排序。
**凡是"格式化函数偷偷改了顺序"这种事，都会在某个下游悄悄吃掉你的意图。**

## 5. 离子：为什么 Fe²⁺ 是 3d⁶ 而不是 3d⁴4s²

这是 Prompt 第九节记过的坑，也是本日算法里最需要理解的一点。

**直觉上错的推导**：Fe 填充顺序是 `... 4s² 3d⁶`，逆着填充顺序拿掉 2 个电子，
4s 是最后填的，所以先掉 4s？

**这个推理的问题**：填充顺序讲的是"电子从哪进来"，电离讲的是"电子从哪出去"。
进和出遵循不同的规则 —— 进入看能量高低，出去看**离核远近**。

物理事实：
- 4s 是最外层，离核最远，受到的束缚最弱。
- 一旦 3d 开始填电子，3d 与 4s 的能量关系会发生调整（电子间排斥改变），
  实际在过渡金属原子里，**4s 上的电子反而更容易失去**。
- 实验证据：Fe²⁺ 的实际排布是 `[Ar]3d⁶`，Fe³⁺ 是 `[Ar]3d⁵`。
  （`3d⁵` 还额外稳定，因为半满 —— 洪特规则的体现。）

所以规则是：

> **先失最外层**：n 大的先失；n 相同时，l 大的先失。

代码：

```cpp
if (cur.n > keep.n || (cur.n == keep.n && cur.l > keep.l))
    best = i;              // 挑出"最该失去电子"的那个亚层
ion.subshells[best].electrons -= 1;
```

用 Fe 验算 Fe³⁺：

| 轮次 | 操作 | 结果 |
|---|---|---|
| 初始 | | 3d⁶ 4s² |
| 1 | n 最大是 4s（n=4） | 3d⁶ 4s¹ |
| 2 | 4s 还有电子，继续 | 3d⁶ 4s⁰ |
| 3 | 4s 空了，次高是 3d（n=3,l=2） | 3d⁵ 4s⁰ |

得到 `1s²2s²2p⁶3s²3p⁶3d⁵`，23 个电子。和实验一致。

> 这就是为什么必须**逐个剥**而不能一次性批量删：Fe³⁺ 的第 1、2 个电子来自 4s，
> 第 3 个来自 3d，涉及两个不同的亚层。批量算会写错。
> 同样的道理也解释了为什么"按填充顺序逆推"会失败 —— 那个顺序里 4s 排在 3d 后面，
> 逆推会先拿走 3d 的电子，得到 `3d⁴4s²`，正是 Prompt 里记录过的那个 bug。

## 6. 阴离子：怎么加电子

阴离子是得到电子。规则简单：按填充顺序（能量从低到高）找**第一个没住满**的亚层，往里塞。

O²⁻ 验算：

| 轮次 | 扫描 | 结果 |
|---|---|---|
| 初始 | | 1s² 2s² 2p⁴ |
| 1 | 1s 满 → 2s 满 → 2p 有 4/6，没满 | 2p⁵ |
| 2 | 1s 满 → 2s 满 → 2p 有 5/6，没满 | 2p⁶ |

得到 `1s²2s²2p⁶`，10 个电子 —— 正好是氖的排布。
这不是巧合：主族元素形成离子时，往往趋向最近的稀有气体构型。

如果所有已知亚层都满了（理论上，如 H⁻ 之后再加），代码会新建下一个亚层补上。
当前 21 个元素的数据用不到这条路径，但留着更安全。

## 7. 校验：为什么值得写三道检查

`loadFromFile()` 在解析完后做了三层校验。写这些代码花的时间，会在第一次手抖改错 JSON 时全部赚回来。

### 第一层：字段范围

`n` 在 1..7、`l` 在 0..3、`l < n`、`0 ≤ e ≤ 容量`。

抓的是"物理上不存在"的写法：`1p` 亚层、`2p` 装了 8 个电子、`l=5`。

### 第二层：电子总数 = 原子序数

```
sum(所有亚层电子数) == atomicNumber
```

**这一条能抓出绝大多数手写错误**。因为它是一个强约束：
不管你哪里写错了，只要总数对不上就会被发现。

代价是：如果有人"错得很对称"（比如 2p 少写 1 个、3s 多写 1 个），总数还是对的。
这种情况第二层抓不住，但极少见，且人眼对照排布式能发现。

### 第三层：离子推算自检

对每个 `commonIons` 里的电荷，真的调一次 `makeIon()`，检查电子数是否等于 `Z - q`。

看起来多余 —— 自己写的函数自己验，不是循环论证吗？

不是。这条检查保护的是 **"数据和算法的一致性"**：

- 数据层（JSON）只存电荷，不存离子的排布。
- 排布由算法算。
- 如果将来有人改了 `makeIon()` 的排序逻辑（比如手贱把 `>` 改成 `<`），
  数据完全没动，但结果全错。
- 有了这条检查，**加载时立刻报错**，而不是等到 Day 16 界面上显示
  `Fe2+ → 3d4 4s2` 时才被人发现。

这是"让错误在最早的时刻、以最明确的方式暴露"的具体实践。

## 8. JSON 结构为什么这么设计

三个具体决定，都有理由：

### ① 亚层用 `{"n":2,"l":1,"e":4}` 而不是字符串 `"2p4"`

字符串方案的好处是可读。但代价是：

- 要写解析器（提取数字、识别字母、处理 `3d10` 这种两位数字）—— 又一个 bug 来源。
- 解析完还是要转成三个整数，等于多绕一圈。
- Day 17 画能级图需要 `n`、`l` 来定位方框位置，字符串得再解析一次。

三个整数是**最贴近使用方的形式**。可读性损失很小（`{"n":2,"l":1,"e":4}` 谁都能看懂）。

### ② 离子只存电荷，不存排布

如果 JSON 里同时存 `"charge": 2` 和 `"subshells": [...]`，就有两个真相来源。
两者不一致时以谁为准？这类问题一旦出现，排查成本极高。

只存电荷，排布算出来，**永远只有一个真相**。配合第三层校验，还能反查算法是否正确。

### ③ 顶层是对象，不是裸数组

```json
{ "version": "1.0", "source": "...", "elements": [ ... ] }
```

裸数组 `[ ... ]` 也能用，但以后想加"轨道形状参数""同位素数据"时，
要么改结构（破坏兼容），要么另开一个文件。
包一层对象，加字段不动现有代码。

**这是纯粹的前瞻性投资，成本一行，收益是将来不用做破坏性改动。**

## 9. 程序运行时到底发生了什么

按时间顺序，从你敲命令到看到输出：

```
$ ./build/molecule_viewer --dump Fe

① 操作系统加载 exe，进入 main()
② 解析命令行：发现 --dump，记下 "Fe"
③ pathutil::resolveResource("assets/data/elements.json")
      ├ 先看当前工作目录有没有 → 有，返回
      └ （没有则查 exe 目录、exe 上级 —— 三级回退）
④ std::ifstream 打开文件                    ← 磁盘 I/O，几十微秒
⑤ nlohmann::json 把约 8 KB 文本解析成树形结构  ← 纯 CPU，几百微秒
      （递归下降解析，每个 { } " : , 都要处理）
⑥ 逐元素读字段 → 填 Element 结构体 → 校验
      ├ 通过 → 塞进临时 vector
      └ 失败 → return false + 错误信息，vector 丢弃
⑦ 全部通过 → elements_.swap(parsed)         ← O(1)，不拷贝
⑧ find("Fe") 线性查找                        ← 21 个元素，纳秒级
⑨ describe() 拼字符串，cout 输出             ← 格式化 + I/O
⑩ return 0，进程结束
```

**关于第 ⑦ 步的 `swap`**：这是 C++ 里实现"要么全成功，要么全不变"的常用手法。
先在临时容器里构建，成功了再一次性换进来。如果中途失败直接 return，
`elements_` 还是原来的（空）状态，不会出现"前 5 个元素能用、第 6 个崩了"的半残状态。
这叫**强异常安全保证**。

**关于性能**：整个数据加载在毫秒级。所以不需要缓存、不需要懒加载、
不需要担心"每次启动都读文件会不会慢"。Prompt 里提到 `element.cpp` 按值返回
`std::vector` 可能有性能隐患 —— 在当前调用频率下（启动一次、查询几十次），
这不是问题。Day 17 每帧画能级图时才需要重新评估（那时会缓存）。
