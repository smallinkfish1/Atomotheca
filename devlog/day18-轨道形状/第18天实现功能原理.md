## 一、轨道形状到底在画什么

### 1.1 波函数可以拆成两个因子

解氢原子的薛定谔方程，得到的波函数可以写成

```
ψ(r, θ, φ) = R(r) · Y(θ, φ)
```

- `R(r)`：**径向**部分，只管「离核多远」，不管方向。
- `Y(θ, φ)`：**角向**部分，只管「朝哪个方向」，不管多远。

拆开的好处是：形状（方向性）完全由 Y 决定，而 Y 只跟量子数 l 有关。
所以「s 是球、p 是哑铃、d 是四叶草」这些结论，只看 Y 就够了。

### 1.2 今天只画 Y，不画 ψ²

严格说，「轨道的形状」指概率密度 |ψ|² 的等值面。它有两个麻烦：

1. 要算 R(r)，而 R(r) 对每个元素、每个主量子数 n 都不一样；
2. |ψ|² 没有硬边界（概率延伸到无穷远），所谓"边界"是人为挑的等值面。

所以教科书画的那种光滑哑铃，画的其实是 **Y 的形状**（严格说是 |Y| 的形状）。
今天跟教科书保持一致，Day 20 再用点云画 |ψ|²。

### 1.3 s 层为什么是球

s 层 l = 0，角向函数是常数：

```
Y(s) = 1 / √(4π)
```

它不随 θ、φ 变。所以对任意方向，半径都相同 → 球。

### 1.4 p 层为什么是「两个相切的球」

p 层 l = 1，角向函数正比于 cos θ，其中 θ 是从 z 轴量起的极角：

```
Y(p_z) ∝ cos θ        →        r(θ) = |cos θ|
```

取绝对值是因为"形状"只看距离，不看符号（符号是相位，见第九节）。

下面就证明：把 `r = cos θ` 绕 z 轴转一圈，得到的曲面是一个球。

## 二、`r = |cos θ|` 是一个球的证明

### 2.1 从球坐标换到直角坐标

球坐标 (r, θ, φ) 和直角坐标的关系：

```
x = r sin θ cos φ
y = r sin θ sin φ
z = r cos θ
```

到 z 轴的距离记作 ρ：

```
ρ = √(x² + y²) = r sin θ
```

### 2.2 代入 r = cos θ

只看上半部分 θ ∈ [0°, 90°]，此时 cos θ ≥ 0，绝对值可以去掉：

```
z = r cos θ = cos θ · cos θ = cos² θ
ρ = r sin θ = cos θ · sin θ
```

### 2.3 消掉 θ

要证的结论是：`ρ² + (z − 1/2)² = 1/4`（这是半径 1/2、球心在 z = 1/2 的球）。
直接代入验证：

```
(z − 1/2)² + ρ²
= (cos²θ − 1/2)² + (sinθ cosθ)²
= cos⁴θ − cos²θ + 1/4 + sin²θ cos²θ
= cos⁴θ − cos²θ + 1/4 + (1 − cos²θ) cos²θ
= cos⁴θ − cos²θ + 1/4 + cos²θ − cos⁴θ
= 1/4
```

成立。所以 θ ∈ [0°, 90°] 那半个 p 轨道**就是一个球**。

### 2.4 下半部分

θ ∈ [90°, 180°] 时 cos θ < 0，取绝对值后 r = −cos θ。同样的推导会得到
`ρ² + (z + 1/2)² = 1/4` —— 关于原点对称的另一个球。

两个球在原点相切（都过原点），合起来就是课本上的哑铃。

### 2.5 所以代码里根本没有"造型"

```cpp
out.lobeRadius = extent * 0.5f;
const float d  = extent * 0.5f;
appendSphereLobe(out.lobeRadius, -ax * d, ...);   // 球心在 −R/2
appendSphereLobe(out.lobeRadius,  ax * d, ...);   // 球心在 +R/2
```

没有贝塞尔曲线、没有手工控制点。这是数学结论的直接翻译。

## 三、半透明为什么必须排序

### 3.1 alpha 混合到底是什么

半透明不是"把颜色调淡"，而是**把新颜色和已有的颜色按比例混合**：

```
最终颜色 = 新颜色 × α + 已有颜色 × (1 − α)
```

α = 0.3 的意思：这个像素上有 30% 来自我，70% 来自我后面的东西。

### 3.2 混合不可交换

假设先画 A（α = 0.5，红色），再画 B（α = 0.5，蓝色），背景是黑色：

```
先 A 后 B：A 落在黑上 → 0.5·红 + 0.5·黑 = 暗红
           B 落在暗红上 → 0.5·蓝 + 0.5·暗红 = 暗紫

先 B 后 A：B 落在黑上 → 0.5·蓝 + 0.5·黑 = 暗蓝
           A 落在暗蓝上 → 0.5·红 + 0.5·暗蓝 = 暗紫偏红
```

结果不一样。所以**必须**按一个确定的顺序画，而物理上正确的顺序是
「从远到近」——因为光是从远处穿到近处再到眼睛的。

### 3.3 为什么排序单位是"瓣"

如果拿整个 p 形状的中心（原点）算距离，两瓣的距离永远相同，
排序结果取决于哪个先进数组 —— 这是隐式的、随机的顺序。

物理上两瓣是分开的两个物体，各自有中心。所以按瓣心排序才对应真实的光路。

### 3.4 一只球内部也要分两层

一只球有近半球和远半球。远半球先画、近半球后画，才是正确的光路。

代码里靠两次 `glDrawElements` 实现：

```cpp
glCullFace(GL_FRONT);  // 剔除朝相机的面 → 只剩远半球
画
glCullFace(GL_BACK);   // 剔除背向相机的面 → 只剩近半球
画
```

"哪个面朝向相机"由三角形的**绕序**决定（第 3、6 天讲过的 CCW）。
这也是为什么 `--dump-orbital` 要专门检查绕序：绕序反了，
这两次剔除会正好反过来。

## 四、深度写入为什么要关

### 4.1 深度缓冲只能记住"最近的一个"

深度缓冲每个像素只存一个数：目前画过的东西里，离相机最近的是多远。
新片段比它近就通过（并覆盖它），比它远就丢弃。

这对不透明物体是正确的：最终你只看得见最近的那个。
但对半透明就错了：**近的东西不会"挡住"远的东西，它会和它混合。**
远的那层也必须留在颜色缓冲里参与混合。

### 4.2 所以才要 glDepthMask(GL_FALSE)

关掉深度**写入**后，深度缓冲仍然是"画不透明物体时留下的那张地图"
（原子在哪里），但半透明片段不再更新它。于是：

- 被原子挡住的轨道片段：深度测试失败 → 不画（正确，因为它确实在原子后面）；
- 轨道自身的两瓣、两半球：深度测试都跟"原子那张地图"比，彼此不干扰
  → 都能画上去，由我们手动的排序决定混合顺序（正确）。

### 4.3 忘了还原会怎样

`glDepthMask(GL_FALSE)` 是一个**全局状态**，不会自动恢复。如果画完轨道不写回 `GL_TRUE`：

- 下一帧画原子时，深度缓冲里没有原子的深度了；
- 于是后画的原子会盖住先画的原子，不管谁在前面；
- 表现是"转视角时原子互相穿透"，而且**时好时坏**（取决于哪一帧刚好设置了状态）。

这类 bug 最难查，因为它跟帧序有关。所以 `drawOrbitals` 结尾三条还原是必须的：

```cpp
glDepthMask(GL_TRUE);
glDisable(GL_BLEND);
glCullFace(GL_BACK);
```

## 五、Fresnel 让球看起来像"壳"

### 5.1 现象

玻璃球、肥皂泡的共同点：正对着看几乎透明，边缘却很清楚、很亮。
原因是**掠射角处反射率高**（Fresnel 效应）。光线斜着擦过表面时，
更容易被反射而不是穿透。

### 5.2 公式

着色器里用的是简化版：

```glsl
float facing = clamp(abs(dot(N, V)), 0.0, 1.0);   // 1 = 正对，0 = 相切
float rim    = pow(1.0 - facing, 2.5);            // 边缘趋近 1
float alpha  = clamp(baseAlpha + rim * 0.55, 0.0, 0.95);
```

- `dot(N, V)`：法线和视线方向的夹角余弦。正对时 = 1，相切时 = 0。
- `1 - facing`：把"正对程度"翻成"掠射程度"。
- `pow(..., 2.5)`：指数控制边缘那圈的**宽度**。指数越大，亮边越窄。
  10 是一条极细的线，1 是整球都发亮。
- `abs()`：背面法线翻过一次之后点积会变号，取绝对值统一处理。

### 5.3 为什么不直接用常数 alpha

常数 alpha 的球，整个表面亮度一致，大脑会读成"一个扁平的圆盘"。
加了 Fresnel 之后，边缘亮、中心透，大脑才读成"一个壳"——
因为它符合真实世界的反射规律。

## 六、为什么把渲染拆成两个函数

原来的 `renderFrame` 里，原子和键是连着画的（一共约 90 行）。
今天把这 90 行原样搬进 `drawMoleculeOpaque()`，然后：

```cpp
if (moleculeVisible)
    drawMoleculeOpaque(...);     // 不透明

if (g_orbital.visible)
    drawOrbitals(...);           // 半透明
```

**一行渲染逻辑都没改**，纯粹是搬家。理由是"代码结构应该表达依赖关系"：

- 如果两个阶段挤在一个函数里、只靠缩进和注释区分，
  加第三个透明物体时很容易又写到原子前面去 —— 编译器不会拦你，
  画面也只在特定角度才出问题；
- 拆成两个函数之后，"透明在后"变成了调用顺序，一眼能看到。

这是架构铁律 1（`main.cpp` 只做调度）的具体落实。

## 七、为什么还要一个 ASCII 版

`--dump-orbital` 打印的是**几何本身**，不是渲染结果：

```
vertices / triangles   网格规模，用来发现"只生成了一个瓣"这类问题
lobes                  瓣心坐标，排序正确性的前提
bbox                   哪根轴最长 → 对称轴对不对
normal len             法线是否单位长度（Fresnel 和光照都依赖它）
on surface             每个顶点是否落在解析曲面上（半径算错会在这里暴露）
winding                三角形绕序（正反面剔除全靠它）
degenerate             极点退化三角形数量（96 / 192 是正常的，不是错误）
slice                  ASCII 剖面，肉眼核对形状
```

这些量在窗口里**看不出来**：绕序错了，画面只是"暗一点"或"内壁发亮"，
没有经验的人根本不会怀疑是绕序。而一个数字就能定位。

这和无显卡环境无关——即使有显卡，验证几何也应该看数字，
因为"看起来对"不等于"数学上对"。

## 八、一个自己踩到的坑：把退化三角形当成"绕序反了"

第一版自检直接判 `dot(几何法线, 顶点法线) <= 0` 就是"反了"，结果 s 球报
**96 / 2304 反了**。

96 = 48 × 2，正好是两极的三角形数。原因：UV 球的南北极**整圈顶点重合**，
极点三角形的两条边长度为 0，叉积恒为 0，`dot = 0` 于是被判成"反了"。

正确做法是先判退化：

```cpp
if (glen <= 1e-6f * e1len * e2len) { ++degenerate; continue; }   // 面积≈0，跳过
if (dot <= 0) ++reversed;                                        // 这才叫反了
```

修完：`reversed = 0`，`degenerate = 96 / 192`。

教训是：**检查器本身也会写错**。当检查结果和预期不符时，
先怀疑检查器，再怀疑被测对象——尤其当错误数量是个整齐的倍数时。
