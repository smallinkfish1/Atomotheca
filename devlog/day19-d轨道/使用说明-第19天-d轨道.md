# 第 19 天 · 3D d 轨道（使用说明）

> 版本 **0.2.1**｜Atomotheca 模块第 5 天｜上一版 0.2.0 只有 s / p
>
> 一句话：今天把轨道形状从 4 个扩到 9 个，新增的五个 d 轨道不再是「球拼出来的」，
> 而是真的按球谐函数把一个球面变形出来。

---

## 一、今日目标

1. `ShapeKind` 扩到 9 个：`d_xy`、`d_yz`、`d_xz`、`d_x2-y2`、`d_z2`。
2. 新增通用路径 `buildHarmonicShape()`：按角向函数 `f(方向)` 做径向变形。
3. `ShapeMesh` 增加**逐瓣索引区间**，让三角形数不同的瓣也能正确排序绘制
   （`d_z2` 的腰环 5184 个三角形，两极各 2016 个）。
4. 面板的形状选择从一排单选按钮改成下拉框（9 个按钮一行放不下）。
5. `--dump-orbital` 扩到九种形状，并新增一项独立校验：**有向体积**。

今天不碰元素数据库、周期表、能级图，也不改渲染流程的顺序。

## 二、核心概念

### 1. l 每加 1，就多一个节面

角量子数 `l` 决定角向函数的「形状复杂度」，而复杂度可以精确地数出来：

| l | 轨道 | 节面数 = l | 形状 |
|---|---|---|---|
| 0 | s | 0 | 球 |
| 1 | p | 1 | 两个相切的球（哑铃） |
| 2 | d | 2 | 四瓣梅花，或「两瓣 + 腰环」 |

节面（nodal surface）是波函数等于 0 的地方。在 `r = |f(方向)|` 这个画法里，
节面就是**半径被压到 0 的那些方向**——曲面在那里被捏成一个点。
所以 d 轨道看起来像「四个球从原点长出来」，而不是四个球各自独立。

### 2. 五个 d 不是五种形状，而是同一类形状的五个朝向

l = 2 有 5 个实球谐函数（这就是「d 亚层最多放 10 个电子」的几何来源：5 个轨道 × 2 个自旋）：

| 名字 | 角向部分 | 长什么样 |
|---|---|---|
| `d_xy` | `2xy` | 四瓣，瓣在 x-y 平面的对角线上 |
| `d_yz` | `2yz` | 同上，转到 y-z 平面 |
| `d_xz` | `2xz` | 同上，转到 x-z 平面 |
| `d_x2-y2` | `x²−y²` | 四瓣，瓣正好在 x、y 轴上（相当于 `d_xy` 转 45°） |
| `d_z2` | `(3z²−1)/2` | **两瓣沿 z 轴 + 赤道一圈腰环** |

前四个互为旋转，所以 `--dump-orbital` 里它们的体积完全相同（都是 0.8127）；
只有 `d_z2` 是另一类（0.5159）。这不是巧合，是可以拿来当校验的事实。

### 3. `d_z2` 为什么长得不一样

`f = (3z²−1)/2`，令它等于 0：`z = ±1/√3 ≈ ±0.577`。
也就是说**节面不是平面，而是两个圆锥面**（半顶角 54.7°，化学里叫魔角）。

- `|z| > 0.577`（两极）：f 为正，半径从 0 涨到 1 → 两瓣。
- `|z| < 0.577`（赤道带）：f 为负，取绝对值后半径又从 0 涨到 0.5 → 腰环。

所以 `d_z2` 的剖面是「大瓣 — 细腰 — 小裙 — 细腰 — 大瓣」。
ASCII 剖面能直接看到这个结构：

```
    ...............|...............
    .............#####.............
    ...........#########...........
    ...........#########...........
    ............#######............
    .............#####.............
    ---------#############---------
    .............#####.............
    ............#######............
    ...........#########...........
    ...........#########...........
    .............#####.............
    ...............|...............
```

### 4. 为什么 s / p 用「球拼」，d 必须真的变形球面

第 18 天已经证明过：`p` 的 `r = |cos θ|` 在直角坐标里就是「半径 1/2、球心在 ±1/2 的球」，
球拼是精确解，而且 4608 个三角形就够。

d 没有这种巧合。要硬用球拼，四个瓣就不是球面（瓣的横截面不是圆），
拼出来的形状在 `--dump-orbital` 的「on surface」一栏会立刻露馅
（顶点不在解析曲面上，误差不为 0）。所以今天老老实实做通用变形：

> 取一个 UV 球的所有方向 `d̂`，把半径改成 `r = f(d̂) · extent`，
> 顶点放在 `d̂ · r` 上。

一句话：**球拼是特例，变形是通法**。

## 三、架构

### 两条生成路径，一个出口

```
buildShape(kind, extent, mesh)
   ├── S            → appendSphereLobe（1 个球）
   ├── Px/Py/Pz     → appendSphereLobe × 2（两个相切球，精确解）
   └── d 系列       → buildHarmonicShape（96×48 球面按 f 变形）
```

三条路都填同一个 `ShapeMesh`，所以 `main.cpp` 的渲染、`orbital_panel.cpp` 的 UI
完全不知道自己拿到的是哪种产物。

### 今天唯一的结构性改动：逐瓣索引区间

第 18 天假设「同一形状里每瓣三角形数相同」，渲染时用
`第 k 瓣偏移 = k × 每瓣索引数`。d 打破了这个假设：

| 形状 | 每瓣三角形数 |
|---|---|
| `s` | 2304 |
| `p_*` | 2304 / 2304 |
| `d_xy` 等 | 2310 / 2302 / 2302 / 2302 |
| `d_z2` | 2016 / 2016 / 5184 |

`d_z2` 的腰环包了 5184 个三角形（它是整条赤道带），两极各 2016。
还用「总长 ÷ 瓣数」的话偏移量会全部错位——画面上表现为**几个瓣拼错位置**。

所以 `ShapeMesh` 加了两个数组：

```cpp
std::vector<int> lobeFirst;   // 每瓣在 indices 里的起始下标
std::vector<int> lobeSize;    // 每瓣的索引个数
```

渲染侧只是把「算偏移」换成「查表」，绘制顺序、两阶段混合、剔除规则全都没动。

## 四、代码实现

### 4.1 角向函数表

```cpp
float angularAbs(ShapeKind kind, float x, float y, float z)
{
    switch (kind)
    {
        case ShapeKind::Px: return std::fabs(x);
        case ShapeKind::Py: return std::fabs(y);
        case ShapeKind::Pz: return std::fabs(z);

        case ShapeKind::Dxy:   return std::fabs(2.0f * x * y);
        case ShapeKind::Dyz:   return std::fabs(2.0f * y * z);
        case ShapeKind::Dxz:   return std::fabs(2.0f * x * z);
        case ShapeKind::Dx2Y2: return std::fabs(x * x - y * y);
        case ShapeKind::Dz2:   return std::fabs(0.5f * (3.0f * z * z - 1.0f));

        default: return 1.0f;   // s
    }
}
```

输入必须是**单位向量**。系数（2、1/2）是实球谐函数的归一化因子，
选成让 `max|f| = 1`，于是所有形状的瓣尖都落在 `extent` 上，切换形状时大小不跳。

注意 `p` 写成 `|x|` 而不是 `|cos θ|`：单位向量上 `cos θ` 就是那个分量本身，
少一次三角函数。

### 4.2 变形一个球面

```cpp
const float theta = kPi * i / kHarmStack;         // 从 +z 量起的极角
const float st = std::sin(theta), ct = std::cos(theta);

for (int j = 0; j <= kHarmSector; ++j)
{
    const float phi = 2.0f * kPi * j / kHarmSector;
    const float dir[3] = { st * std::cos(phi), st * std::sin(phi), ct };

    const float r = angularAbs(kind, dir[0], dir[1], dir[2]) * extent;
    const float p[3] = { dir[0] * r, dir[1] * r, dir[2] * r };
    // 法线见 4.3
}
```

分段数从 s / p 的 48×24 提到 **96×48**：四瓣梅花的分界比球的经纬线更挑分辨率，
48 段时瓣的边缘会出现明显的锯齿状折线。96×48 一个有 9216 个三角形，
五个 d 加起来 46k，对显卡是零负担。

> 节面附近半径趋近 0，网格在那里被「捏尖」，会产生一批面积几乎为 0 的退化三角形
> （`d_z2` 192 个、`d_xy` 244 个）。这是 `r = |f|` 画法固有的，不是 bug，
> 自检里单独统计、不算错误。

### 4.3 法线：不对方程求导，直接算隐函数梯度

要解析地求 `∂/∂θ`、`∂/∂φ` 的叉积，公式又长、在节面附近还会除以 0。换个思路：

曲面写成隐函数 `F(p) = |p| − f(p̂) · extent = 0`，
那么 **`∇F` 就是朝外的法线方向**（梯度指向函数增大的方向）。

```cpp
float levelFunction(kind, x, y, z, extent)   // = |p| − f(p̂)·extent

// 中心差分求梯度，h = extent / 1000
gx = F(x+h) - F(x-h);  gy = ...;  gz = ...;
n  = normalize(gx, gy, gz);          // 失败就退回径向（极少发生）
```

六个采样点换掉一整套解析推导，而且永远不会除零。

### 4.4 绕序：算出来的，不是摆出来的

UV 网格的固定索引顺序在球面上是「从外看逆时针」，但变形之后曲面会翻折，
某些三角形的叉积方向会反过来。与其手工推「哪种形状要反着写索引」，
不如让程序自己判断：

```cpp
// 几何法线 g = e1 × e2，顶点法线之和 sn
if (dot(g, sn) < 0)  swap(b, e);   // 反了就把后两个索引换位
```

这样「从外看逆时针」对所有形状都成立，`--dump-orbital` 里
`winding: 0 / 9216 reversed` 才有意义——它验证的是这条断言，而不是碰巧。

### 4.5 分瓣：按最近的瓣心归类

排序的单位是瓣，所以每个三角形要归到某一瓣上：

1. 先定义瓣心：四瓣梅花在对角线上（`(±1,±1,0)/√2 × 0.55·extent`），
   `d_z2` 是 **两极各一个 + 腰环以原点为中心**（共 3 瓣）。
2. 每个三角形算重心，归到最近的瓣心。
3. 按瓣把索引拼回去，同时记下 `lobeFirst / lobeSize`。

`d_z2` 的腰环瓣心取原点，排序时它的深度正好落在两极之间——先画远瓣、
再画腰环、最后画近瓣，遮挡关系是对的。

### 4.6 渲染：只换了偏移量的来源

```cpp
// 第 18 天
const std::size_t first = lobeIndex * perLobe;
const GLsizei     count = perLobe;

// 第 19 天
const std::size_t first = app.orbLobeFirst[kind][lobeIndex];
const GLsizei     count = app.orbLobeSize[kind][lobeIndex];
```

其余一行没改：仍然「远瓣 → 近瓣」、「每瓣先背面后正面」、「关深度写入」。
瓣数上限从 4 提到 8（`d_z2` 是 3，留余量）。

### 4.7 UI：单选按钮 → 下拉框

9 个按钮一行放不进 340px 的面板，改成 `BeginCombo` 循环 `Selectable`。
颜色仍然来自 `orbital::shapeColor()`，面板里的字色和 3D 里的颜色还是同一份数据。
公式提示也从写死的 `r = |cos theta|` 改成 `orbital::shapeFormula(kind)`，
和 `--dump-orbital` 打印的是同一个字符串。

### 几何自检（今天的主验证手段）

```bash
./build/molecule_viewer --dump-orbital          # 九个全打
./build/molecule_viewer --dump-orbital dz2
./build/molecule_viewer --dump-orbital dx2-y2   # 连字符、^ 都认
```

九个形状的关键数字（都是这一版实测）：

| 形状 | 三角形 | 瓣 | 体积 mesh / 解析 | 退化三角形 |
|---|---|---|---|---|
| `s` | 2304 | 1 | 4.1590 / 4.1888（99.3%） | 96 |
| `p_x` | 4608 | 2 | 1.0397 / 1.0472（99.3%） | 192 |
| `d_xy` | 9216 | 4 | 0.8017 / 0.8127（98.7%） | 244 |
| `d_yz` | 9216 | 4 | 0.8029 / 0.8127（98.8%） | 336 |
| `d_xz` | 9216 | 4 | 0.8029 / 0.8127（98.8%） | 288 |
| `d_x2-y2` | 9216 | 4 | 0.8017 / 0.8127（98.7%） | 386 |
| `d_z2` | 9216 | 3 | 0.5096 / 0.5159（98.8%） | 192 |

非 100% 是正常的：网格是「用平面三角形逼近曲面」，内接多面体必然略小于真实体积。

**今天新增的独立校验 —— 有向体积**：

```
V = (1/6) Σ p0 · (p1 × p2)        ← 散度定理
```

它和法线、绕序**都不相关**：法线是用来定绕序的，绕序又是用几何法线定的，
两个互相印证等于自证。体积是从三角形本身积分出来的独立量，能抓到方向性错误。

**这项校验上线第一时间就抓到了一个真错**：我手写解析体积时把两个半径 R/2 的球
算成了 `πR³/6`，正确是 `πR³/3`（少乘了 2），于是 `p` 的体积比是 198.6%。
改对之后三个 p 全部 99.3%。这条教训值得记住：**校验要选和被测对象不共享假设的量**。

## 六、排错清单

| 现象 | 根因 | 处理 |
|---|---|---|
| 切到某个 d 后，几个瓣的位置错乱 | 还用「总长 ÷ 瓣数」算偏移 | 必须用 `lobeFirst / lobeSize` 逐瓣取 |
| `d_z2` 的腰环把两极的瓣整块盖住 | 腰环瓣心没设成原点，排序时深度算错 | 腰环的瓣心是 `(0,0,0)` |
| 某个 d 一看就是纯色块 | 顶点法线算成 0（节面附近退化） | 差分梯度失败时退回径向法线 |
| 剖面图只看到四个点 | 剖面选错了平面（`d_xz` 要用 x-z 面） | 按 `shapeKind` 选平面，见 `describeShape` 末尾 |
| 剖面图看得到形状但 3D 里是反的 | 绕序没统一，背面剔除剔掉了外表面 | 每个三角形用 `dot(叉积, 顶点法线和)` 判一次，反了就换索引 |
| `volume` 一栏偏差 200% | 解析体积写错（漏乘 2 / 除错系数） | 先手算一遍：球体积 4/3πR³ |
| 打开面板看到 `###` 或方块 | ImGui 默认字体只有 ASCII | 名字一律用 `d_xy` 这种 ASCII 写法，别用 `x²−y²` |
| 下拉框里选了没反应 | 动态网格没建（`setupOrbitalMeshes` 只建了 4 个） | `SHAPE_COUNT` 现在是 9，循环上界自动跟着走 |

## 九、遗留

1. **窗口效果未实机验证** —— 需要你在真桌面切到 `d_z2` 转一圈，确认
   「腰环夹在两瓣之间」的遮挡关系，以及边缘 Fresnel 是否还在。
2. **两瓣/四瓣同色** —— 物理上相邻瓣的波函数符号相反（`+ / −` 相位），
   今天还是整形状一个颜色。要表达相位就得再加一套配色规则。
3. **没有 f 轨道（l = 3，7 个）** —— 数据层只到 Kr，连 4f 都没有，先不做。
4. **轨道仍画在分子中心**，不跟随单个原子。
5. **`d` 的网格是 96×48 固定分辨率** —— 没有 LOD，也没有按形状自适应
   （四瓣梅花其实比 `d_z2` 更吃分辨率）。
6. **体积校验的容差是 5%** —— 目前都在 2% 以内，但更细的节面会让误差变大，
   到时候要改成「按三角形数估计误差」。

- **能看到 d 轨道了**。按 `O` 打开面板，下拉框里现在有九项：
  `s`、`p_x`、`p_y`、`p_z`、`d_xy`、`d_yz`、`d_xz`、`d_x2-y2`、`d_z2`。
- **形状是按球谐函数真算的**。四瓣梅花的瓣在对角线上、`d_x2-y2` 的瓣在坐标轴上、
  `d_z2` 是两瓣加一圈腰环——都能在 `--dump-orbital` 的 ASCII 剖面里核对。
- **换了公式会直接显示**。面板里那行 `angular part: r = |2xy|` 跟着当前形状变，
  和命令行打印的是同一个字符串。
- **自检更硬了**。除了点数、包围盒、法线、绕序、曲面误差，现在还比对
  **有向体积**——这条能抓到「法线和绕序一起算错」这种互相掩盖的问题。

### 10.3 命令行变化

```bash
./molecule_viewer --dump-orbital                       # 九个全打
```

### 10.4 顺带修掉的问题

- 第 18 天渲染代码里「每瓣索引数相同」的隐含假设被显式化：现在每瓣自己记账，
  `d_z2` 那种大小不一的瓣不会错位。
- `insideShape`（ASCII 剖面用）原来对 p 用「落在某一瓣球内」判断，现在统一成
  `|p| ≤ f(p̂)·extent`，三种形状共用一条判据，剖面图和 3D 里的形状不可能对不上。
- 我手写的解析体积公式（`πR³/6`）被新校验当场抓出，已改成 `πR³/3`。

### 10.5 这个版本还不行的地方

- 只有一个颜色：没表达 `+ / −` 相位（教科书里常画成两种颜色）。
- 没有 f 轨道；轨道不跟随原子；d 的网格分辨率是固定的。
- **窗口效果未实机验证**，只到编译级 + 几何自检。
